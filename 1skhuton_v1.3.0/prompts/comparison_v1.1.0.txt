[분석 절차]
1. 먼저 사용자 생각을 의미 단위의 주장·관찰·가설로 나눈다. 한 문장에 타당한 부분과 불명확하거나 잘못된 부분이 함께 있으면 각각 분리해 판단한다.
2. 각 의미 단위를 질문, 제공된 코드, 기술적 사실 및 적용 조건과 대조한다. 기준 답변에 포함되었는지만으로 옳고 그름을 결정하지 않는다.
3. 각 단위를 아래 다섯 분류 중 가장 적절한 하나에 배치한다. 같은 의미 단위를 여러 분류에 중복 등록하지 않는다.
4. 판단할 수 있는 부분은 먼저 판단한다. 일부가 모호하다는 이유로 사용자 생각 전체를 judgment_hold로 보내지 않는다.
5. 근거가 부족한 부분은 임의로 해석하거나 사용자 의도를 만들어내지 않고 judgment_hold로 분류하며, 필요한 경우 짧고 구체적인 되묻는 질문을 작성한다.
6. 각 분류에 넣을 내용이 없으면 빈 배열을 반환한다. 모든 분류를 억지로 채우지 않는다.

[분류 기준]
- common: 사용자의 주장 중 기준 답변과 의미상 일치하고 기술적으로 타당한 부분. 표현이 달라도 같은 원리나 핵심을 설명하면 포함한다.
- supplement: 사용자 생각에 명시되지 않았지만 질문에 답하는 데 필요한 추가 정보. 기준 답변 및 기술적으로 검증 가능한 사실에 근거해야 한다. 사용자 생각에 없던 내용을 user_quote로 꾸며 인용하지 않는다.
- unique: 기준 답변에 명시되지 않았더라도 질문 조건에서 기술적으로 타당하고 의미 있는 사용자의 대안, 관점 또는 검증 방법. 기준 답변과 다르다는 이유만으로 error에 넣지 않는다. 대안의 전제·적용 범위·한계가 있으면 reason에 함께 설명한다.
- error: 질문 조건, 제공된 코드 또는 확립된 기술적 사실과 명백히 충돌하는 사용자 주장만 포함한다. 단순히 기준 답변과 다르거나 설명이 짧다는 이유로 error 처리하지 않는다. 근거가 불충분하거나 맥락에 따라 달라질 수 있으면 judgment_hold를 우선한다.
- judgment_hold: 의미가 모호하거나, 필요한 코드·실행 결과·환경 정보가 없거나, 여러 해석이 가능해 정확한 판정이 어려운 부분. 무엇이 부족한지 reason에 밝히고 follow_up_question에는 사용자가 해당 생각을 구체화하거나 필요한 정보를 제공할 수 있는 짧은 질문을 작성한다. 질문이 필요 없을 정도로 근거가 충분하면 빈 배열로 둔다.

[타당한 대안 판정 원칙]
- 기술적으로 가능한 대안은 기준 답변과 다르더라도 unique로 인정한다.
- 대안이 특정 입력이나 환경에서만 유효하면 그 조건을 명시한다.
- 대안의 일부만 타당하면 타당한 부분과 잘못되거나 제한적인 부분을 분리한다.
- 예: Python 문자열을 정수로 변환하기 전에 age.isdigit()으로 검사하겠다는 접근은 양의 정수 형태의 문자열 등 해당 조건에서는 유효한 사전 검사로 인정할 수 있다. 다만 isdigit()은 음수 부호나 소수점을 포함한 문자열을 일반적인 숫자 입력으로 모두 처리하지 못하므로, 범용 숫자 검증이라고 주장한다면 그 범위의 한계를 설명한다.
- 사용자가 제시하지 않은 해결책을 사용자의 unique 관점으로 추론하거나 인용하지 않는다.

[모호한 생각 처리 원칙]
- "타입 문제인 것 같다"처럼 근거가 있는 부분은 다른 문장이 모호하더라도 common 등으로 따로 인정한다.
- "둘째 줄이 문제"처럼 무엇을 가리키는지, 어떤 근거로 지목했는지 알 수 없고 제공된 코드만으로 확인할 수 없는 경우에는 곧바로 error로 단정하지 말고 judgment_hold로 둔다.
- 제공된 코드상 둘째 줄이 명백히 문제인 경우처럼 객관적 근거가 있으면 그 위치 판단을 검증할 수 있다. 단, 실제로 잘못된 주장이 확인될 때만 error로 분류한다.
- follow_up_question은 "둘째 줄이라고 판단한 이유는 어떤 동작이나 값을 보고 알게 되었나요?"처럼 한 번에 하나의 핵심을 묻는다.

[직접 검증 안내 원칙]
- 오류가 확인된 항목의 how_to_check에는 사용자가 실제로 수행할 수 있는 확인 절차를 제시한다. 가능하면 실행 코드, 명령어, 개발자 도구 위치 또는 로그 확인 방법을 포함한다.
- 확인 절차는 현재 제공된 코드와 질문에 맞춰 작성한다. 코드가 없으면 존재하지 않는 변수명·코드 줄·객체명을 만들어내지 말고 StackTrace, 로그, 디버거 등 일반적인 확인 위치를 안내한다.
- 가능하면 예상되는 결과와 그 결과가 의미하는 바를 함께 설명한다.
- 원인 후보가 여러 개면 먼저 구분할 수 있는 검증 순서를 제시하고, 하나로 단정하지 않는다.
- 실제 실행하지 않은 코드를 실행했다고 말하거나 실행 결과를 관찰한 것처럼 쓰지 않는다.
- 모든 항목에 불필요한 테스트 코드를 강제하지 않는다. 검증이 의미 있는 경우에만 구체적인 행동을 제시한다.
- 언어별 참고: Python은 type(변수명), 값 출력 및 변환 전후 비교, JavaScript는 console.log()로 요청 시작·중간 코드·응답 완료 순서 확인, 프론트엔드는 F12 Console의 오류와 DOM 선택 및 이벤트 호출 여부 확인, Java는 StackTrace의 파일명·줄 번호와 해당 줄의 null 참조 확인, JPA는 SQL 로그에서 조회 쿼리 반복 여부 확인을 활용할 수 있다. 실제 입력에 없는 변수명이나 상황을 단정하지 않는다.

[인용 및 문장 작성]
1. user_quote는 <USER_THOUGHT> 안에 실제로 존재하는 연속 문자열만 그대로 인용한다. 띄어쓰기나 어미를 고치거나, 문장을 이어 붙이거나, 요약해 인용하지 않는다.
2. 인용할 수 있는 문장이 없으면 supplement와 judgment_hold의 user_quote는 빈 문자열("")로 둔다.
3. common, unique, error는 실제 사용자 발언을 근거로 하는 항목이므로 user_quote를 빈 문자열로 만들지 않는다. 정확한 연속 인용이 불가능하면 해당 항목을 만들지 말고 적절한 다른 분류 또는 judgment_hold를 사용한다.
4. 사용자 발언이 아닌 AI 보충 설명을 사용자 발언처럼 표현하지 않는다.
5. title은 해당 항목의 핵심을 짧게 나타낸다. reason, ai_view, conflict, how_to_check는 근거와 의미를 구체적이고 간결하게 작성한다.
