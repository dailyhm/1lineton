사용자 코드:
<USER_CODE>
{{{{CODE}}}}
</USER_CODE>

[질문 유형 규칙]
허용 유형은 CONCEPT, DEBUGGING, PROBLEM_SOLVING, DESIGN 네 가지뿐이다.
입력으로 전달된 유형을 그대로 사용한다. 유형을 새로 분류하거나 다른 유형으로 바꾸지 않는다.
- CONCEPT: 정의, 원리, 적용 조건을 스스로 설명하도록 유도
- DEBUGGING: 재현 조건, 원인 가설, 확인 방법을 생각하도록 유도
- PROBLEM_SOLVING: 요구사항, 해결 접근, 예외, 검증 방법을 생각하도록 유도
- DESIGN: 선택 조건, 대안, 장단점, 선택 근거를 생각하도록 유도

[수행 작업]
1. chat_title을 만든다. 첫 질문의 핵심을 사람이 실제 대화방 제목으로 쓸 법한 자연스러운 질문형 문장으로 요약한다. 최대 50자다. 질문의 의도를 바꾸거나 새로운 주제를 추가하지 않는다.
2. chat_summary를 만든다. 첫 질문에서 다룰 핵심 확인 대상을 짧은 구절로 설명한다. 예: "중간 실패와 동시성 조건을 살펴보기". 최대 80자이며, 단어만 나열하지 말고 무엇을 이해하거나 확인할지 자연스럽게 쓴다.
3. choices 3개를 만든다. 서로 다른 사고 방향을 제시하고 정답이나 완성 코드를 직접 공개하지 않는다.
4. hints 정확히 2개를 만든다. 각 항목은 사용자가 정답을 바로 알지 않고 한 단계씩 생각하도록 돕는 짧은 질문형/행동형 힌트 문자열이다. 힌트는 look_at/try_this와 중복되지 않게 별도 작성한다. 첫 번째 힌트는 작은 단서, 두 번째 힌트는 조금 더 구체적인 단서다.
5. guidance 정확히 2개를 만든다. 각 항목에는 반드시 look_at과 try_this가 함께 있어야 한다.
   - look_at: 사용자가 어디를 봐야 하는지 알려주는 짧은 관찰 대상이나 키워드다. 겉핥기식으로 간결하게 쓰고, 행동 절차나 긴 설명을 넣지 않는다. 예: "반복문의 종료 조건", "실패가 발생하는 시점".
   - try_this: 사용자가 실제로 무엇을 해보면 되는지 알려주는 구체적인 행동 지침이다. 완전한 문장으로 작성하고, 값을 직접 계산하기, 특정 부분 비교하기, 조건을 바꿔 보기 등 실행 가능한 행동을 포함한다. 단순히 "확인해 보세요"라고 끝내지 않는다.
   - 두 필드는 하나의 안내 항목으로 묶여 함께 공개된다. look_at은 살펴볼 위치, try_this는 그 위치에서 수행할 행동이다.
   - 정답이나 완성 코드를 바로 알려주지 말고, 사용자가 스스로 답을 발견할 수 있는 단계만 제시한다.
6. 비교 분석에 사용할 기준 답변을 만든다. 질문에 직접 답하고 핵심 원리, 근거, 적용 조건을 포함한다. 사용자가 이해하기 쉬운 자연스러운 설명으로 작성한다. 코드 실행을 했다고 주장하지 않는다.
6. 질문이나 코드에 [REDACTED]가 있으면 민감정보가 마스킹된 자리표시자로 취급하고 원래 값을 추측하지 않는다.

[출력 규칙]
아래 JSON Schema에 맞는 JSON 객체만 출력한다. choices는 정확히 3개, hints는 정확히 2개의 문자열, guidance는 정확히 2개이며 chat_title은 50자 이하, chat_summary는 80자 이하다.
question_type, example_sentence, session_id 등 지정되지 않은 필드는 출력하지 않는다. hints 문자열 배열과 guidance 객체 배열은 서로 독립된 필드로 반드시 모두 출력한다.
기준 답변, hints, guidance는 서버 내부에 보관한다. 공개 API는 chat_title, chat_summary, choices만 반환하고, hints와 guidance는 각 전용 API로 단계별 제공한다.
